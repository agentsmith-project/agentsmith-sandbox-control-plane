# Sandbox Manager（manager-service）最终评价与迭代建议

日期：2026-01-20  
范围：`manager-service/`（HTTP API、K8s 交互、文件上传/下载、可观测性、配置系统）  
验证基线：本地真实 kind 环境可跑通 `manager-service/scripts/e2e-test.sh`

---

## 1. 总体评分（10 分制）

- 功能完整度：**7.5/10**（核心 API 链路齐全：create/touch/exec/upload/download/delete，且有真实 kind E2E 覆盖）
- 架构设计：**7/10**（`internal/*` 分层边界清晰；入口/可执行程序组织符合 Go 最佳实践）
- 代码实现质量：**6.5/10**（总体可读，但仍存在“可用但不严谨”的实现点，会影响长期维护）
- 可测试性：**5/10**（基本依赖 shell E2E，缺少 Go 单元/组件测试，回归成本高）
- 可运维性：**7/10**（health/ready/metrics/debug config/config watcher 已具备；但观测数据准确性与结构化仍需加强）
- 安全性：**6.5/10**（已有路径校验/大小限制等基础防线；上传解包安全策略仍需明确与可验证；文档/流程需避免明文敏感信息）

> 结论：当前是“可上线试运行”的工程质量，但要达成“可长期稳定迭代、低回归成本、可观测可排障”的生产级标准，还需要补齐测试与观测、并加固上传安全策略。

---

## 2. 主要优点（保持并延续）

- **边界清晰**：`internal/httpapi` 做协议与编排，`internal/k8s` 负责集群交互，`internal/files` 负责 tar 流处理，可维护性较好。
- **可跑的真实集成验证**：kind E2E 能覆盖关键链路，能作为“冒烟与集成回归”的底线保障。
- **配置与调试能力**：提供 debug config、metrics、config watcher 等基础运维能力，具备继续扩展空间。

---

## 3. 主要问题（当前最影响质量/效率的点）

### 3.1 缺少 Go 层测试金字塔

- 现状：几乎没有 `*_test.go`；主要依赖 shell E2E。
- 影响：定位慢、回归慢、边界条件难覆盖；容易出现“误判根因 → 引入 workaround → 代码变重且不可验证”的循环。

### 3.2 观测数据不够准确/可用

- 现状：HTTP 指标记录存在“固定 status code”等简化实现，会导致 metrics 失真。
- 影响：线上排障与容量评估会被误导；问题出现时难以快速归因（是 API 错误还是客户端错误，是否集中在某类 endpoint）。

### 3.3 上传/解包是天然高风险面，策略需要明确且可验证

- 现状：已做路径前置校验与大小限制，但对 tar 内容（symlink/hardlink/路径穿越/绝对路径/特殊文件）缺少明确且可测试的“强保证”策略。
- 影响：安全风险与不可预期行为风险；后续引入更多功能时容易踩坑。

### 3.4 路由与 handler 组织存在脆弱点

- 现状：部分路由通过 `strings.Contains/HasSuffix` 判断。
- 影响：新增 endpoint 时容易出现误匹配或遗漏；代码可读性与演进成本上升。

### 3.5 文档/配置治理需要制度化

- 现状：历史上 dev 文档可能出现明文凭据（即使是临时用于排查，也应避免）。
- 影响：安全与合规风险；团队协作的信任成本上升。

## 4. 最重要的迭代建议（按优先级）

### P0：建立最小可用的 Go 测试体系（强烈建议先做）

目标：用单测/组件测试兜住“核心逻辑正确性”，把 kind E2E 退化为“集成冒烟”。

建议落地：
- **为 `internal/k8s.Executor` 增加单测**：验证构建 exec URL 时 `stdin/stdout/stderr/tty/command/container` 参数正确（这类错误应做到“测试一跑就挂”）。
- **为 `internal/files` 增加单测**：覆盖路径校验、maxBytes、tar stderr 错误判定分支。
- **为关键 handler 做组件测试**（可用 `httptest`）：至少覆盖错误码与输入校验（例如 invalid path、upload too large、timeout 参数边界）。

收益：显著降低回归成本；避免再次引入“不可证伪/不可解释”的 workaround。

### P0：修正 HTTP 观测准确性（否则 metrics 不可信）

目标：让 metrics 成为可靠信号源。

建议落地：
- 增加 `ResponseWriter` wrapper 捕获真实 `status code` 与响应字节数。
- metrics 标签策略避免高基数（例如对 path 做 pattern 化：`/v1/sandboxes/{id}/...`）。

收益：线上问题能快速定位（失败率、慢请求、热点 endpoint）。

### P1：加固上传/解包安全策略（并可测试验证）

目标：把“上传 tar.gz 解包”的行为定义清楚，并能通过测试证明不会越界/不会引入链接类风险。

建议落地：
- 明确并实现拒绝：symlink/hardlink/绝对路径/`..` 路径穿越/特殊文件（device、fifo 等）。
- 方案选择：
  - 最佳：解包前扫描 tar entry（两段式：先读目录再解包）并做强校验；
  - 或：在容器端用更严格的 tar 参数/过滤策略（但需确认 runner 镜像 tar 行为与版本）。
- 为以上策略补齐单测 + 增加 1~2 条 E2E 用例防回归。

收益：降低安全风险与不可预期行为，提升对外接口的“契约稳定性”。

### P1：路由与 handler 组织重构（小成本提升可维护性）

目标：降低新增 API 时的错误率，提高可读性。

建议落地：
- 用更明确的路由匹配（pattern 化），避免 `Contains("/files/upload")`。
- 将 `/v1/sandboxes/{id}` 相关路由收敛成清晰的路由表（便于审查与扩展）。

收益：减少逻辑分叉与误匹配，便于团队协作。

### P2：文档/配置治理制度化

目标：避免敏感信息进入仓库，避免环境差异导致“本地能跑线上不行”。

建议落地：
- 增加 secret pattern 扫描（pre-commit/CI）。
- 文档只提供模板与变量名，不出现真实凭据；敏感信息只走环境变量/本地私有文件。

收益：降低安全风险与协作摩擦。

---

## 5. 建议的迭代里程碑（可执行）

- Milestone A（1~2 天）：P0 测试骨架 + `internal/k8s.Executor` 单测落地 + CI/脚本能稳定跑 `go test ./...`
- Milestone B（1~2 天）：P0 metrics 修正（真实 status/bytes + path 归一化），并在 kind E2E 中验证 metrics 增量正确
- Milestone C（2~4 天）：P1 上传解包安全策略落地（含单测 + 少量 E2E）
- Milestone D（1~2 天）：P1 路由重构（保持 API 兼容，重点提升可读性与扩展性）

---

## 6. 质量门禁建议（长期）

- 必须：`gofmt`、`go test ./...`（即使无测试也必须保证可编译）
- 必须：kind E2E 作为合并前的集成冒烟（至少覆盖 upload/download/exec）
- 推荐：每次改动新增或调整对应的单测（把回归成本“左移”）
